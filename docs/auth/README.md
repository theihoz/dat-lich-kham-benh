# Phiên và khôi phục tài khoản

Browser gọi `/api/v1/auth/login` bằng JSON `{email,password}`. Response chứa `accessToken,userId,email,role`; không có refresh token. Server đặt `clinic_refresh` HttpOnly, SameSite=Strict, path `/api/v1/auth`, Secure trong prod. Client chỉ giữ access token trong bộ nhớ; điều hướng/tải lại sẽ phục hồi qua cookie. localStorage chỉ chứa id/email/role cho giao diện; giá trị này không có quyền xác thực.

Browser gửi POST `/api/v1/auth/refresh` và `/logout` với cookie, `Origin` đúng origin `APP_PUBLIC_URL`, header `X-CSRF-Token: clinic`. Browser tự đặt Origin; header này cùng kiểm tra Origin chống CSRF. Không đọc cookie bằng JS. Chỉ phục vụ frontend và API cùng origin; cấu hình CORS không cho website khác đọc auth response. Web Locks serialize refresh giữa các tab hỗ trợ API đó, single-flight serialize trong một tab. Trên browser không hỗ trợ Web Locks, hai tab refresh cùng token có thể kích hoạt bảo vệ replay và yêu cầu đăng nhập lại.

Client API/Postman có thể yêu cầu chế độ token bằng header `X-Auth-Client: api` khi login, sau đó refresh/logout cùng header và JSON `{refreshToken}`. API mode không đọc cookie và không đặt cookie. Nếu request có Origin thì Origin vẫn phải khớp. Client phải lưu refresh token ở nơi bảo mật; không sử dụng chế độ này trong frontend. API access vẫn gửi `Authorization: Bearer ...`. JWT refresh cũ trước nâng cấp không được chấp nhận. Không gọi refresh token trực tiếp vào API dữ liệu.

Mỗi refresh token là 32 byte ngẫu nhiên URL-safe; DB chỉ lưu SHA-256. Rotation tiêu thụ token cũ dưới user row lock; dùng lại thu hồi cả family (kể cả access JWT thuộc family). Logout thu hồi family đang dùng. Đổi/reset mật khẩu tăng credentials_version và thu hồi mọi family; access JWT so phiên bản DB tại mỗi request. Trong prod, token không có session family bị từ chối. Không dùng access token từ localStorage.

POST `/forgot-password` và `/resend-verification` nhận `{email}`, luôn trả thông báo chung. `/reset-password` nhận `{token,password}` (8–72 ký tự; BCrypt giới hạn 72 byte UTF-8); `/verify-email` nhận `{token}`. Token được hash, khóa theo user, có expiry30phút/24giờ và một lần dùng. Yêu cầu liên kết mới thu hồi liên kết cũ cùng loại. Link chỉ được tạo từ `APP_PUBLIC_URL`; token ở URL fragment, trang xóa fragment khỏi history trước gửi POST. Link không tự thực hiện thay đổi khi mail scanner mở trang. Production yêu cầu email_verified; migration đặt false cho tài khoản hiện có, cần gửi xác minh hoặc quy trình quản trị xác minh thực tế. Demo/test seed được đánh dấu verified bằng mặc định Java; tài khoản public register mới có email_verified=false.

Account email dùng durable outbox chung với notification delivery; token thô cần xuất hiện trong link email/outbox. Không ghi token vào application log. Bảo vệ DB/queue/backup và áp dụng retention của outbox sau gửi. Response login/refresh có Cache-Control no-store; proxy không được cache auth.

Rate limiting dùng Redis atomic Lua trong prod và memory có giới hạn trong demo/test. Per remote IP + endpoint: login10/phút, refresh60/phút, register/reset/verify5/giờ. 429 kèm Retry-After; Redis lỗi thì fail-closed503, không fallback local trong prod. Reverse proxy phải cấu hình nguồn forwarded header tin cậy; không cho client tùy ý giả IP. Chỉ tắt limiter bằng `app.auth.rate-limit.enabled=false` cho test có chủ đích. Các giới hạn mặc định có thể ảnh hưởng nhiều người dùng chung NAT; cần đo và điều chỉnh trước pilot.

Fragment `schema-auth.sql` được root tích hợp Flyway. Không tự chạy fragment trên production đang có dữ liệu. Auth user FKs ON DELETE CASCADE giữ hành vi admin xóa tài khoản chưa có lịch sử khám. Giữ dữ liệu refresh/action cũ cho replay detection đến hết TTL; cần tác vụ retention vận hành để xóa an toàn sau expiry, không xóa session đã rotation trước hết TTL.
