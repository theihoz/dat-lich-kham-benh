# Durable notifications and medical audit

Booking confirmation, cancellation, appointment reminders and account emails use `notification_outbox` in the same database transaction as their business change. An after-commit Observer wakes the dispatcher; a periodic scan recovers lost wakeups after restart. Account links use the configured `app.public-url` and URL fragments. The nine-field `EmailNotificationMessage` contract and Factory Method/Adapter remain unchanged.

The dispatcher locks up to 20 due rows, sends persistent AMQP messages with a stable `messageId`, requests mandatory routing and waits for correlated publisher confirmation. A nack, returned message, timeout or connection failure leaves the row pending with exponential backoff; eight failures mark it `DEAD`. Operational recovery must inspect dead rows, correct the failure, and reset their status/next-attempt time without changing their message ID. Do not copy payloads to issue trackers or logs: these contain personal data and account links. No public retry endpoint is provided.

The consumer inserts and flushes an insert-only receipt before SMTP and commits the receipt after SMTP succeeds. The unique message ID serializes concurrent duplicate deliveries. Failed transactions retain no receipt and can retry. The listener tries three times with bounded backoff, then rejects into `<email-queue>.dlq` through `<email-exchange>.dlx`. Fix the underlying failure before authorized redrive; preserve message ID and `notificationKind` header. Do not route DLQ automatically back to the main queue.

Delivery is **at least once**. A crash after broker confirmation but before outbox commit can publish again; receipts handle that duplicate. A crash after SMTP accepts a message but before receipt commit can send a duplicate email. SMTP does not offer an atomic transaction with the database, so this code does not promise exactly-once email delivery. The local demo transport uses the same durable paths and receipt handling but sends only into the bounded demo inbox.

Every minute, the reminder scan selects confirmed appointments starting within the next 24 hours. Appointment locks serialize cancellation and reminder creation; unique `APPOINTMENT_REMINDER:<booking-code>` event keys prevent repeat scheduling across instances/restarts. The consumer rechecks the appointment under a lock and drops reminders that have since been canceled/completed or have already started. Clinic times use `app.clinic-zone` (default `Asia/Ho_Chi_Minh`); delivery/audit timestamps are stored in UTC.

Configuration: `app.delivery.poll-delay-ms` (5000), `reminder-delay-ms` (60000), `initial-delay-ms` (15000), `max-publish-attempts` (8), `confirm-timeout-seconds` (5), `scheduling-enabled` (true). Scheduled jobs and asynchronous wakeups are disabled in the `test` profile so tests explicitly drive dispatch. Production must enable scheduling; multiple instances are safe through database locks and unique constraints. Monitor `clinic.notifications.outbox.pending`, `clinic.notifications.outbox.dead`, `clinic.notifications.publish` and `clinic.notifications.consume`, alongside RabbitMQ queue/DLQ depth.

## Upgrade existing queues

RabbitMQ refuses to redeclare an existing queue with different DLX arguments. Before enabling this version on an existing deployment, pause new writes and drain the old consumer queue. Stop legacy consumers, remove the old binding once the queue is empty, then configure a new queue (for example `EMAIL_QUEUE=clinic.email.queue.v2`) for this version. Do not leave both queues bound to the same routing key. Legacy messages lack the stable message ID and must be drained through the legacy consumer or deliberately migrated with an audited unique ID; the new consumer rejects messages without an ID. Do not delete a queue containing undelivered messages.

## Medical access audit

Doctor reads/writes and patient medical-record list reads store actor, action, record/appointment IDs and timestamp in `medical_audit_entries`. Authenticated principal identity takes precedence over a service argument. Denied doctor access is recorded in a separate committed transaction, so the denial's rollback cannot erase the event. Successful writes create a before/after revision in `medical_record_revisions` in the same transaction as the medical record and appointment status change. Application logs do not include clinical text. No audit/revision endpoint is exposed; restrict direct database access and backups, including outbox, receipts, audit and revision tables. Audit rows deliberately retain identifiers without cascading foreign keys so account removal cannot erase evidence. Retention/encryption policies and authorized access must be configured by the operator before handling real patient data.

`docs/schema-delivery.sql` is the additive schema fragment incorporated into the versioned Flyway migration. Do not apply both independently to an existing database.
